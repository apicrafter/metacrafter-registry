# Metacrafter Registry — Audit (2026-11-04)

This audit covers the repository state at commit `f168bf8` ("Release 1.02").
It is the evidence base for the OpenSpec change
[`modernize-registry-platform`](../openspec/changes/modernize-registry-platform/proposal.md).

All numbers were computed directly from the YAML sources in `data/` (not from
the builder's `stats` output, which overstates completeness — see §2).

## Summary

- **The public registry is offline.** `https://registry.apicrafter.io` resolves
  (Cloudflare) but the origin times out. Every `datatype_url` / `classurl` that
  metacrafter emits points at this host, so all links printed by metacrafter
  scans, and written into DataHub, OpenMetadata and Atlas, are dead today.
  GitHub Pages is not enabled for the repository (404).
- **Formal validity is 100%. Real completeness is low.** All 642 records
  (630 datatypes and patterns, 12 tools) pass the Cerberus schema. Only 122
  records (19%) have a regexp, examples, links and a doc of 60+ characters.
  207 records (33%) have no regexp, no examples and no links.
- **The builder's statistics are misleading.** It counts empty strings and
  empty lists as "present". It reports 85.7% with regexp, 92% with Wikidata
  and 100% with examples. The real figures are 47%, 16% and 32%.
- **About a third of the records are bulk-generated stubs.** Commit `0d81040`
  (2026-01-01) added 216 files that scripts generated from metacrafter-rules
  keys. 77 records have `doc` equal to `name`, or a doc shorter than 25
  characters.
- **The ecosystem is misaligned.**
  - 39 metacrafter-rules keys, used by 43 rules, have no registry entry.
  - 125 registry IDs have no rule.
  - The `metacrafter` tool record lists 48 supported types, but the rules
    repo covers 505 registry IDs.
- **There is no CI, no release process and no tests.** Build outputs are
  committed by hand.

## 4. Consistency issues

- **ID styles are mixed.** There are four conventions:
  - 475 IDs have no prefix.
  - 107 concatenate the country code (`usssn`, `uscity`).
  - 20 use a `rus` prefix (`rusfirstname`).
  - 28 use a `cc_` prefix (`am_ssn`, `ru_vehicle_plate`).

  The README asks for the `cc_` prefix but grandfathers the rest.
- **180 file names (29%) differ from their `id`.** Examples:
  `us_ssn.yaml → usssn`, `us_soc.yaml → ensoc`, `se_passport.yaml → sepassport`.
- **Schema typing is weak.**
  - `is_pii` is a string.
  - `parent` is a dict `{type: <id>}` instead of an ID.
  - `translations` mixes two shapes: 40 plain strings and 103 `{name, doc}`
    dicts.
  - Empty strings are used instead of omitting a field.
  - The "schemes" are Cerberus rule dicts, not JSON Schema. External tools and
    editors cannot use them.
- **Patterns duplicate data.** All 58 patterns carry their own `categories`,
  although the README says they inherit them. 22 datatypes also hand-maintain
  a `patterns:` list, which the builder then overwrites with embedded pattern
  objects.
- **Two pseudo-codes need modelling.** `common` is used as a language for 213
  records. `EU` is used as a country for 11 records. Both are legitimate needs
  ("language-independent", "supranational region"), but neither is modelled
  explicitly.
- **PII flags are inconsistent.** 29 datatypes have `is_pii: 'True'` but no
  `pii` category.
- **Directory and country disagree.** 2 records (defects #2 and #3) are in a
  directory that does not match their `country` field.

## 5. Provenance and licensing

- Many `doc` and `translations.*.doc` texts are verbatim Wikipedia ledes. For
  example, the `email` doc includes the pronunciation and the "(hence e- + mail)"
  aside. Wikipedia text is CC BY-SA 4.0, but the repository is Apache-2.0
  with no data license or attribution. The data needs an explicit license, and
  copied text needs attribution or rewriting.
- Records have no provenance fields, so there is no way to tell:
  - who added a record, or when;
  - which source it came from;
  - whether a human reviewed a generated stub.

## 6. Tools

- There are 12 tool records:
  - pii: 5
  - other: 4
  - detector: 2 (`metacrafter`, `metacrafterpro`)
  - catalogs: 1
- Together they reference only 150 of the 630 IDs.
- Supported-type lists are maintained by hand and are stale. `metacrafter`
  lists 48 types, but the rules repo actually covers 505 registry IDs.
- The schema allows `catalogs`, but the README does not document it.

## 7. Code and infrastructure

- `scripts/builder.py` (677 lines):
  - Builds, validates, reports and computes stats.
  - Writes outputs before checking uniqueness.
  - Assumes every pattern's parent has `is_pii`.
  - Its stats treat empty values as present.
- The loader and dictionary helpers are copied into at least 6 scripts.
  `export.py` uses a CWD-relative `DATA_PATH = '../data'`.
- Four one-off generator scripts (`generate_missing_entries.py`,
  `batch_create_missing.py`, `add_missing_identifiers.py`,
  `analyze_missing_registry_entries.py`) produced the 2026 stubs. They are not
  part of any documented workflow.
- `src/registry.py` is a dynamic Flask server, but it only serves precomputed
  JSON. Nothing in it requires a server.
- The repository has:
  - no `pyproject.toml`
  - no tests
  - no CI
  - no release tags
  - no CHANGELOG
- `.idea/`, `.DS_Store` and `metacrafter.code-workspace` are committed.
- `_original/` (legacy CSV) and `analysis/` (DataHub and Sherlock notes,
  `.xlsx`) are research leftovers. `analysis/README.md` itself says they will
  be moved.
- `AGENTS.md` points to `openspec/AGENTS.md`, which did not exist before this
  change.

## 8. Ecosystem integration (current contract)

**metacrafter**

| What | Where |
|---|---|
| Per-datatype link | `metacrafter/classify/processor.py:221` hardcodes `https://registry.apicrafter.io/datatype/{dataclass}`, which feeds `classurl` and `datatype_url` |
| JSON client | `metacrafter/registry/client.py` reads `{base}/registry.json` (dict keyed by id) and `{base}/datatype/{id}.json` |

- The env override `METACRAFTER_REGISTRY_URL` is not honoured by the processor.
- The JSON client is currently used only by tests.
- **Contract to preserve:** `/datatype/<id>` (no extension, no trailing
  slash), `/datatype/<id>.json` and `/registry.json`.

**metacrafter LLM mode and metacrafter-llm**

- They read a **local** `datatypes_latest.jsonl`, found by relative paths
  such as `../metacrafter-registry/data/…`.
- They embed `id`, `name`, `doc`, categories, countries, languages, example
  values and `regexp`.
- The committed ChromaDB index in metacrafter-llm holds 407 entries, so it is
  stale against 630.

**`metacrafter/scripts/ecosystem_check.py`**

- Reads `data/datatypes_latest.jsonl` from a sibling checkout and compares it
  with rule `key`s.

**metacrafter-rules**

- 214 files, 1267 rules (804 field, 463 data), 544 distinct keys.
- 39 keys have no registry entry. Examples: `email_person`, `date_date`,
  `boolean_boolean`, `lat_geo`, `de_iban`, `ca_sin`, `mime_type`. Most come
  from `common/common.yaml`, `common/geo.yaml` and the `ca`/`de` PII files.

**AI and MCP**

- There is no MCP server anywhere in the ecosystem.
- The only AI integration is the RAG classifier.

## 10. Conclusion

The core asset is in good shape: one-file-per-entity YAML in git, with stable
IDs that metacrafter already links to. The problems sit around that core:

- The site is down.
- Completeness is overstated, and generated stubs are not marked as such.
- Typing and naming are inconsistent.
- No surface is designed for machines and agents.

The proposed change keeps YAML in git as the source of truth and makes the
rest a reproducible build that deploys to GitHub Pages. The build produces:

- a static site;
- a static JSON API, keeping the legacy URLs;
- agent-oriented outputs: `llms.txt`, Markdown twins, OpenAPI, JSON-LD/SKOS,
  an MCP server and a Python package.

Quality gates in CI make the numbers above impossible to regress.
