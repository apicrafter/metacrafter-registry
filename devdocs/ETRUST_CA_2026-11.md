# Анализ выгрузки реестра аккредитованных УЦ e-trust.gosuslugi.ru (слепок 2023-03-14)

Цель: найти в выгрузке прежней версии портала e-trust.gosuslugi.ru (реестр
аккредитованных удостоверяющих центров) значения, которые реестр не
идентифицирует, и предложить для них семантические типы.

## Источник и метод

- Файл `data-profiles/apibackuper-profile/etrust/data.jsonl.zst`. Выгрузку
  сделал apibackuper 2023-03-14 через API
  `POST /app/scc/portal/api/v1/portal/ca/list` (6 страниц по 100 записей).
- В выгрузке 512 удостоверяющих центров (УЦ), 1562 программно-аппаратных
  комплекса (ПАК), 2078 ключей уполномоченных лиц, 2336 сертификатов и 3208
  адресов списков отзыва. Записи вложенные: 36 листовых путей JSON.
- Кроме полей JSON разобраны:
  - строки `КемВыдан` и `КомуВыдан` (Distinguished Name издателя и
    владельца). Из них получено 34 атрибута;
  - поле `Данные`, сертификат X.509 в Base64 без PEM-заголовков. Разобраны
    2335 из 2336 сертификатов (asn1crypto). Из них взяты атрибуты subject и
    issuer по OID, алгоритмы, расширения и строки расширений
    `subjectSignTool` и `issuerSignTool`.
- Для каждого поля запущен `Registry.identify()` на всех различных значениях
  (до 400), с именем поля и `country=RU`. Затем кандидатные регулярные
  выражения проверены на **всех** различных значениях. Ниже «попадание» —
  доля различных значений, совпавших с выражением.
- Смысл OID сверен с текстом приказа ФСБ России от 27.12.2011 № 795
  «Об утверждении Требований к форме квалифицированного сертификата…»
  (п. 17, 18, 27–30).
- Скрипты и промежуточные данные (`profile.json`, `certs.json`,
  `identify.json`) лежат во временном каталоге сессии и в репозиторий не
  входят.

## Главный вывод

Реквизиты организации реестр определяет уверенно: ИНН (10 цифр), ОГРН,
email, URL, дата и время, почтовый индекс, код страны. Не определяется всё,
что относится к инфраструктуре открытых ключей (PKI): строки DN,
сертификаты в Base64, серийные номера, идентификаторы ключей, классы
средств ЭП, номера сертификатов ФСБ. Для этих полей `identify` ничего не
находит или выбирает ложный тип:

| Поле | Что это | Что выдаёт `identify` |
|---|---|---|
| `КемВыдан`, `КомуВыдан` | Distinguished Name | ничего |
| `Данные` | сертификат X.509, Base64 DER | ничего; поиск идёт ~1,7 с на значение (см. `molformula`) |
| `СерийныйНомер` | серийный номер сертификата | `bban` (45) |
| `ИдентификаторКлюча` | Subject Key Identifier | `sha1hash` = `ripemd160hash` = `torrent_info_hash` (60) |
| `Отпечаток` | SHA-1 отпечаток сертификата | то же; `x509_certificate_fingerprint` не находится |
| `КлассСредствЭП` | класс средства ЭП (КС1…КА1) | `gml_id` (37) |
| `СтатусАккредитации.Статус` | статус аккредитации УЦ | `gml_id` (37) |
| `РеестровыйНомер` | номер УЦ в реестре | `udkindex` (54) |
| `СредстваУЦ`, `subjectSignTool` | наименование СКЗИ / средства УЦ | ничего (≤ 15) |
| `issuerSignTool[2]`, `[3]` | реквизиты сертификата / заключения ФСБ | ничего (≤ 10) |
| ИНН в сертификате (OID 1.2.643.3.131.1.1) | ИНН юрлица, дополненный до 12 цифр нулями | `inn` (65), у издателя ниже `uic_wagon_number` (79) |
| `ST` / `S` в DN | «код субъекта + наименование» | `okved_code_name` (44–60) |
| СНИЛС в DN | СНИЛС | `oktmo` (62); `rusnils` не находится |

Пробелы сосредоточены в двух местах:

1. **Общие типы PKI** (не только российские). Строка DN, сертификат в
   Base64 без PEM-обрамления, серийный номер, идентификатор ключа,
   отпечаток без разделителей. Такие поля есть в любой выгрузке
   сертификатов: журналы Certificate Transparency, хранилища сертификатов,
   инвентаризация PKI, LDAP и Active Directory.
2. **Российская регуляторика ЭП.** Классы средств ЭП по приказам ФСБ
   № 795/796, номера сертификатов соответствия и заключений ФСБ, статус и
   реестровый номер аккредитованного УЦ, а также 12-значная запись ИНН
   юрлица в старых квалифицированных сертификатах.

## Кандидаты в новые типы

Предложенные `id` — рабочие названия. Регулярные выражения проверены
только на этой выгрузке.

### Приоритет 1: общие типы PKI

| Кандидат | Поля | Формат / проверка | Значений | Попадание |
|---|---|---|---|---|
| `x500_distinguished_name`: строковая запись Distinguished Name (RFC 4514 и вид, который выводят CryptoAPI и OpenSSL) | `КемВыдан`, `КомуВыдан` | `^AT=[^=]*(?:,\s*AT=[^=]*)+$`, где `AT` = `(?:[A-Za-zА-ЯЁа-яё][A-Za-zА-ЯЁа-яё0-9-]*\|(?:OID\.)?[0-2](?:\.\d+)+)` | 1528 | 100 % |
| `x509_certificate_der_base64`: сертификат X.509 в Base64 без строк `-----BEGIN…`. Паттерн записи `x509_certificate` | `Данные` | `^MII[A-Za-z0-9+/]{2}[DTjz]CC[A-Za-z0-9+/]{3}gAwIBAgI[A-Za-z0-9+/]+={0,2}$` | 2336 | 100 % |
| `x509_serial_number`: серийный номер сертификата, шестнадцатеричный, до 20 октетов (RFC 5280, 4.1.2.2) | `СерийныйНомер` | `^[0-9A-Fa-f]{2,40}$`, распознаётся по имени поля | 2336 | 100 % |
| `x509_key_identifier`: идентификатор ключа (subjectKeyIdentifier / authorityKeyIdentifier, RFC 5280, 4.2.1.1–4.2.1.2) | `ИдентификаторКлюча` | `^[0-9A-Fa-f]{40}$` (метод 1 RFC 5280: SHA-1 открытого ключа), распознаётся по имени поля | 2077 | 100 % |

Пояснения:

- Выражение для DN построено на парах «атрибут=значение». Значение может
  содержать запятые (`STREET=ул. Радио, дом 24, корпус 1`), но не знак
  `=`. В выгрузке встречаются русские имена атрибутов (`ИНН`, `ОГРН`,
  `СНИЛС`, `ИННЮЛ`), `S` и `ST` для региона, `E` для email и
  `OID.1.2.643.100.4`. Выражение совпадёт и с произвольной строкой вида
  `ключ=значение, ключ=значение`. Чтобы этого не было, можно потребовать
  хотя бы один атрибут из `CN|O|OU|DC|UID` (lookahead).
  Пример: `CN=Минкомсвязь России, ИНН=007710474375, ОГРН=1047702026701, O=Минкомсвязь России, STREET=улица Тверская, дом 7, L=г. Москва, ST=77 Москва, C=RU, E=dit@minsvyaz.ru`.
- Выражение для Base64 опирается на структуру DER. Первая группа символов
  `MII…` кодирует `SEQUENCE` с длиной в двух байтах. Затем идёт
  `tbsCertificate` (`…CC…`) и поле версии v3 `A0 03 02 01 02`
  (`gAwIBAgI`). Сертификаты v1, без поля версии, и сертификаты длиннее
  16 КБ выражение не покрывает. Пример: `MIIH1DCCB4GgAwIBAgILAKlM9MoAAAAABaEw…`.
- Серийные номера в выгрузке: 20 знаков (1491), 22 (752), 34 (89), все в
  верхнем регистре и чётной длины. Все 752 номера длиной 22 начинаются с
  `00`: это знаковый байт DER. Пример: `00A94CF4CA0000000005A1`. По одному
  формату тип не отличить от любого hex-значения, поэтому без имени поля
  (`serial`, `serialNumber`, `СерийныйНомер`) он не определяется.
- `ИдентификаторКлюча` совпадает с расширением subjectKeyIdentifier
  сертификата у 2076 из 2077 различных значений. Пример:
  `E0986CEDDC7945B1D58115A79A1C75D86601A609`.

### Приоритет 1: российская регуляторика электронной подписи

| Кандидат | Поля | Формат / проверка | Значений | Попадание |
|---|---|---|---|---|
| `ru_es_tool_class`: класс средства ЭП (и средства УЦ) по приказу ФСБ № 796 | `КлассСредствЭП`; в сертификате — политики `1.2.643.100.113.1`–`.6` | `^К(?:С[123]\|В[12]\|А1)$` | 4 (КС2 — 1430 ПАК, КС3 — 125, КВ2 — 4, КС1 — 3) | 100 % |
| `ru_inn_le_padded`: ИНН юрлица в 12-значной записи с двумя ведущими нулями. Паттерн записи `inn` | ИНН в DN и OID `1.2.643.3.131.1.1` | `^00\d{10}$`; контрольная сумма `ru_inn` по последним 10 цифрам | 480 | 100 % (контрольная сумма после отбрасывания `00` — 100 %; без него — 9 %) |
| `ru_ca_accreditation_status`: статус аккредитации удостоверяющего центра | `СтатусАккредитации.Статус`, `ИсторияСтатусовАккредитации…Статус` | `^(?:Действует\|Приостановлена\|Прекращена\|Аннулирована)$` | 4 | 100 % |
| `ru_fsb_conformity_certificate`: номер сертификата соответствия ФСБ России на СКЗИ или средство УЦ | `issuerSignTool[2]`, `[3]` | ядро `СФ/\d{3}-\d{4}`; в данных с префиксами «Сертификат соответствия (ФСБ России) №» и датой «от ДД.ММ.ГГГГ (г.)» | 11 | 100 % ядра |
| `ru_fsb_conclusion_number`: номер заключения ФСБ России о подтверждении соответствия | `issuerSignTool[2]`, `[3]` | ядро `149(?:/\d+)+(?:-\d+)?`, например `149/3/2/2/23`, `149/7/1/4/2-603`; в данных с префиксом «Заключение №» и датой | 6 | 100 % ядра |

Пояснения:

- Приказ ФСБ № 795 (п. 27) задаёт OID классов средств ЭП владельца для
  расширения certificatePolicies: `1.2.643.100.113.1` — КС1, `.2` — КС2,
  `.3` — КС3, `.4` — КВ1, `.5` — КВ2, `.6` — КА1. Классы накопительные:
  сертификат класса КС2 содержит и `.1`, и `.2`. В выгрузке: `.1` — 2335,
  `.2` — 2332, `.3` — 177, `.4` и `.5` — по 6 сертификатов. В значениях
  поля буквы кириллические. В `subjectSignTool` встречается латинская
  запись (`Домен-KC2`).
- ИНН с двумя нулями. В действующей редакции приказа № 795 OID
  `1.2.643.3.131.1.1` — 12-значный ИНН физлица (п. 18), а для
  организации есть отдельный атрибут INNLE `1.2.643.100.4` из 10 цифр. До
  появления INNLE ИНН организации записывали в `1.2.643.3.131.1.1` как
  `00` + 10 цифр. Сертификаты такого вида будут встречаться ещё долго. В
  выгрузке все 478 ИНН владельцев и оба ИНН издателей имеют этот вид.
  Пример: `007710474375` (Минкомсвязь России). Для записи нужен алгоритм
  контрольной суммы, который снимает префикс `00`: текущий `ru_inn`
  принимает лишь 9 % таких значений, и то случайно.
- Статус аккредитации: на момент выгрузки «Приостановлена» — 361 УЦ,
  «Прекращена» — 98, «Действует» — 51, «Аннулирована» — 2. Это перечень,
  который показывает портал. Формулировки нужно сверить с 63-ФЗ «Об
  электронной подписи» (ст. 16) до статуса `stable`.
- Сертификаты и заключения ФСБ. Приказ № 795 (п. 30) требует указывать в
  `issuerSignTool` реквизиты заключения ФСБ о соответствии средства ЭП и
  средства УЦ. На практике УЦ пишут туда и номера сертификатов соответствия
  (`СФ/124-2239`), и номера заключений (`149/3/2/2/23`). Смысл трёхзначного
  кода после `СФ/` (в данных — 121, 124, 128) и префикса `149` в источниках
  не проверен. Описывать его в записи не нужно.

### Приоритет 3: только внутри сертификатов

Эти значения есть только в теле сертификата, в JSON портала их нет.
Запись нужна, если источником будут разобранные сертификаты.

- **Адрес списка отзыва (CRL) и адрес сертификата издателя (AIA).** В
  данных 3195 различных адресов CRL: 99,4 % — `http(s)://…\.crl`,
  остальное — `ftp://`. Формально это `url`. Отдельный паттерн
  (`crl_distribution_point_url`) поможет отличить их от прочих ссылок.
- **keyUsage** — закрытый перечень флагов RFC 5280 (`digitalSignature`,
  `nonRepudiation`, `keyCertSign`, `cRLSign`…). В выгрузке 6 сочетаний.
- **OID российских алгоритмов.** ГОСТ Р 34.10-2001 `1.2.643.2.2.19` —
  1286 сертификатов, ГОСТ Р 34.10-2012 (256 бит) `1.2.643.7.1.1.1.1` —
  1040, (512 бит) `1.2.643.7.1.1.1.2` — 10. Подпись: `1.2.643.2.2.3` и
  `1.2.643.7.1.1.3.2`. Наборы параметров: `1.2.643.2.2.35.1` и др. Формат
  покрывает `oid` (60–72). Отдельная запись — перечень алгоритмов —
  нужна, только если требуется различать значения.
- **unstructuredName «ИНН/КПП/ОГРН»** (`1.2.840.113549.1.9.2`,
  `007810225534/781001001/1027804875560`) — в 10 сертификатах.

### Не предлагаю

- `Псевдоним` ПАК, `Название`, `КраткоеНазвание` — наименования
  организаций. Это `rucompanyname`, у которого нет выражения (см. ниже).
- `Адрес.УлицаДом` — улица и дом одной строкой. Это `street_address` /
  `rustreet`.
- Внутренние поля Microsoft CA (`1.3.6.1.4.1.311.21.1` — версия ключа CA,
  `1.3.6.1.4.1.311.21.2` — хэш предыдущего сертификата CA) — служебные.

## Проблемы существующих записей

- **`molformula`** — экспоненциальный перебор с возвратом (ReDoS). Группа
  `(\)?[¹²³⁴⁵⁶⁷⁸⁹⁰]*[⁺⁻]?)?` может совпасть с пустой строкой двумя
  способами внутри внешнего `(…)+`. Время растёт вчетверо на каждые два
  символа: `'CH'*11 + '!'` (23 символа) проверяется 1 с. На сертификате в
  Base64 проверка останавливается после ~24 букв в начале строки и занимает
  1,7 с на значение. Поэтому `identify` на поле `Данные` (400 значений)
  занимает около 11 минут; первый прогон по всей выгрузке не уложился в
  10 минут. Выражение также совпадает с `RU`, `v3`, `SubCA`.
  Стоит сделать необязательные части взаимоисключающими. Ещё нужен тест
  на время проверки длинной строки.
- **`inn`** — для 12-значной записи ИНН юрлица (`00` + 10 цифр) проходит
  выражение, но не контрольную сумму, и оценка падает до 63–65. У ИНН
  издателя выше оказывается `uic_wagon_number` (79): 12 цифр с проверкой
  Луна. Решение — паттерн `ru_inn_le_padded` (см. приоритет 1).
- **`rusnils`** — нет выражения. СНИЛС в DN (`СНИЛС=`, OID
  `1.2.643.100.3`) получает `oktmo` (62) и `govlicaccount` (61). Нужно
  выражение `^\d{11}$` (и форма `\d{3}-\d{3}-\d{3} \d{2}`) вместе с
  существующей контрольной суммой `ru_snils`.
- **`rusregioncode`** — код региона без ведущего нуля (`2`, `4`, `9`) в
  `Адрес.Регион.Код` не совпадает (попадание 93 %). В итоге `okfs`
  (`^\d{2}$`, `stable`, 60) выигрывает у `rusregioncode` (`draft`, 55).
  Варианты: допустить `^(?:0?[1-9]|[1-9]\d)$` или описать такую форму
  отдельным паттерном.
- **`gml_id`** (`draft`) — выражение NCName совпадает с любым словом,
  включая кириллицу. В этой выгрузке это первый кандидат для 31 поля:
  город, регион, статус, класс СКЗИ, фамилия, должность. Оценки не выше
  37, то есть ниже порога 55. В анализе lawmon2026 решено выражение не
  сужать, чтобы не отходить от спецификации XML. Здесь это подтверждает
  другое: у полей со статусом и классом СКЗИ нет своего типа, и первым
  оказывается самый общий.
- **`x509_certificate_fingerprint`** — выражение принимает только запись с
  двоеточиями. Отпечаток из 40 hex-цифр (`Отпечаток`, так его хранят
  CryptoAPI и порталы) получает три равных кандидата: `sha1hash`,
  `ripemd160hash`, `torrent_info_hash` (60). Нужна компактная форма
  (паттерн или вторая ветвь выражения) и перевод `ru: Отпечаток
  сертификата`, чтобы работало совпадение по имени поля. Во всех 2335
  разобранных сертификатах значение равно SHA-1 от DER сертификата.
- **`x509_certificate`** — только PEM. Сертификаты в Base64 без
  обрамления (`Данные`) не определяются (см. приоритет 1).
- **`okved_code_name`** совпадает с регионом «77 г. Москва» (44–60).
  Паттерн `ru_region_code_name` с именем поля решит это через
  ранжирование. Можно также исключить в выражении двузначный код с
  пробелом.
- **`bban`** (`^[A-Z0-9]{11,29}$`) выбирается для серийных номеров
  сертификатов (45).
- **`ruspostalcode`** делит первое место с `ru_esr_code` (58) и `hexcolor`
  (57): шесть цифр подходят всем трём.
- **Сходство имени поля не работает для кириллицы.** `_tokens()` в
  `client.py` выделяет токены выражением `[a-z0-9]+`, поэтому у имён
  `СерийныйНомер`, `Отпечаток`, `ИдентификаторКлюча`, `РеестровыйНомер`
  токенов нет и надбавка за имя (до 25) равна нулю. Русские переводы
  `translations.ru.name` в сравнении участвуют, но тоже дают пустое
  множество. Для типов, которые различаются только по имени поля
  (серийный номер, идентификатор ключа, отпечаток, реестровый номер), это
  значит, что на русских данных они не побеждают. Та же логика есть в
  `static/identify-core.js`, исправлять нужно обе реализации вместе.

## Замечания о данных

- Персональные данные. В DN 27 сертификатов уполномоченных лиц есть ФИО
  (`SN`, `G`) и СНИЛС физических лиц, а в 68 — должность. Это публичные
  сертификаты, но записи-примеры из них брать нельзя.
- Время. `ДействуетС` записано без часового пояса. `21:00:00` и `20:00:00`
  — это полночь по Москве в UTC (UTC+3 после 2014 года, UTC+4 в
  2011–2014). Дата в таком поле на сутки раньше настоящей. Сроки
  сертификатов (`ПериодДействияС/До`) записаны с `Z`.
- Ошибки ввода. В истории статусов есть дата `2222-01-08`. У одного
  владельца в атрибут INNLE (`ИННЮЛ`, OID `1.2.643.100.4`) записано девять
  цифр `770201001` — это КПП, а не ИНН (5 сертификатов).
- В `КомуВыдан` одни и те же атрибуты записаны по-разному: `S` и `ST`,
  `SN` и `SURNAME`, `G` и `GIVENNAME`, `ИННЮЛ` и `OID.1.2.643.100.4`.
  Это зависит от программы, которая выгрузила строку. Тип
  `x500_distinguished_name` должен допускать все варианты.
- Массовая смена статуса: у 159 УЦ статус изменился 2021-12-31 в
  18:06:58, у 144 — 2021-12-31 в 21:00:01.

## Сделано (2026-11-07)

Шаги 1–4 из порядка работ.

- `molformula`: выражение переписано без неоднозначных пустых групп.
  Необязательный заряд теперь всегда занимает хотя бы один символ, а
  закрывающие скобки и нижние индексы после него начинаются со скобки или
  запятой. На 400 000 случайных и составных строках старое и новое
  выражения дают одинаковый результат. Время проверки линейное:
  `'CH'*11 + '!'` — меньше 1 мс вместо 1 с. Добавлен тест
  `test_repository_regexps_do_not_backtrack_catastrophically`: каждое
  выражение реестра проверяется на коротких «злых» строках и Base64
  сертификата с порогом 0,2 с. Старое выражение `molformula` его не
  проходит (4 с), остальные проходят.
- Общие типы PKI (`any/cryptography`, все `draft`):
  - `x500_distinguished_name` — строка DN; нужны две пары и хотя бы
    один распространённый атрибут;
  - `x509_certificate_base64` — паттерн `x509_certificate`, Base64 DER
    без PEM-строк;
  - `x509_serial_number` — серийный номер, до 21 октета, с двоеточиями
    или без;
  - `x509_key_identifier` — SKI/AKI, 20 или 8 октетов;
  - `x509_certificate_thumbprint` — паттерн
    `x509_certificate_fingerprint`, отпечаток без разделителей. В
    `x509_certificate_fingerprint` добавлен русский перевод.
- `ru_inn_le_padded` — паттерн `inn` для записи `00` + 10 цифр с новым
  алгоритмом `ru_inn_padded` (Python и `identify-core.js`, тесты обоих).
- `rusnils`: выражение `^(?:\d{11}|\d{3}-\d{3}-\d{3} \d{2})$` и примеры.
- Российские типы ЭП (`draft`): `ru_es_tool_class`,
  `ru_ca_accreditation_status`, `ru_fsb_conformity_certificate`,
  `ru_fsb_conclusion_number`, `ru_accredited_ca_regnum`.
